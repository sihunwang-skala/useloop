# 출시 전 검증·개선 제안

> 이 문서는 **현재 상태의 점검 결과와 제안**입니다. 제안 항목은 코드로 활성화하지 않았으며, 법률·정책 판단이 필요한 항목은 [LEGAL_REVIEW.md](../LEGAL_REVIEW.md)와 함께 전문가 검토를 거쳐야 합니다.

## 1. 배포 가능 여부 구분

| 구분 | 상태 | 근거 |
|---|---|---|
| 로컬 Demo (인메모리) | ✅ 동작 | 단위 테스트 54건, 브라우저 E2E 18건, 빌드 통과 |
| Supabase 스키마·RLS·RPC (SQL 로직) | 🟡 부분 검증 | 순수 PostgreSQL + auth 스텁에서 45개 점검 + 동시 발급 테스트 통과. **Supabase 자체(GoTrue/PostgREST/JWT)는 미검증** |
| Supabase 연동 앱 경로 (`store/supabase.ts`, 인증) | ❌ 미검증 | 실제 인스턴스에 연결된 적 없음. 통합 테스트 코드는 작성했으나 **한 번도 실행되지 않음** |
| 공개 서비스 출시 | ❌ 불가 | 아래 "출시 차단 항목" 참고 |

## 2. 출시 차단 항목 (모두 해결 전 실서비스 금지)
1. 테스트 전용 Supabase 프로젝트에서 `tests/integration/supabase-rls.test.ts` 실행·통과 (anon/authenticated 권한, 이메일 확인 정책 포함)
2. 약관·개인정보처리방침·피드백 운영 원칙의 법률 검토 (현재는 샘플)
3. **개인정보 삭제 절차 구현**: 지금은 `deletion_requested_at` 표시까지만 있음. 요청 접수 → 법정 보관 의무 검토 → 실제 삭제/익명화(작성 피드백 포함) → 처리 기한·로그
4. 분산 Rate Limit(Redis 등) 교체. 현재는 프로세스 메모리라 서버리스에서 사실상 무효
5. 이메일 인증 및 봇 방지(CAPTCHA 등) 적용
6. 운영 환경변수 점검: `DEMO_MODE` 미설정/false, Supabase 값 설정 (아래 3번)

## 3. Demo Mode 가 운영에서 쓰이지 않는지 (점검·수정 결과)
- 문제 발견: 기존에는 Supabase 환경변수가 **빠지면 조용히 Demo Mode**가 되어 공개된 데모 계정(관리자 포함, 비밀번호는 소스에 공개)이 운영에서 열릴 수 있었음.
- 수정(`src/lib/config.ts`): `NODE_ENV=production` 에서 Supabase 값이 있으면 `DEMO_MODE=true` 여도 Demo 무시. Supabase 값도 `DEMO_MODE=true` 도 없으면 **500 오류로 기동 거부(fail-closed)**. 단위 테스트로 고정.
- 데모 계정·가상 데이터는 `MemoryStore` 생성 시에만 만들어지며 Supabase 경로에서는 로드되지 않음. SQL 마이그레이션에는 데모 데이터가 없음(카테고리만).
- 데모 세션 쿠키는 production 에서 `Secure`. 데모 서버를 운영 도메인에 두지 마세요(서버리스에서는 인스턴스별로 메모리가 달라 부적합).
- 남은 주의: 로그인 화면이 데모 비밀번호를 그대로 표시하므로 데모는 **인터넷에 공개하지 않는 로컬/내부용**으로만 사용.

## 4. 리스크 검토와 개선안

| 주제 | 현재 | 제안 (미적용) |
|---|---|---|
| **스팸** | 사용자별 시간당 제한(메모리). 방문 기록(`service_visits`)은 anon insert 가능 → 통계 오염 가능 | 방문 기록을 서버 라우트에서만 기록(익명 insert 정책 제거), IP 해시+서비스별 일일 중복 제거, Redis 제한, CAPTCHA |
| **다중 계정** | 이메일 가입만, 확인 절차 없음 | 이메일 인증 필수, 신규 계정 쿨다운, 같은 서비스 피드백 빈도 제한(DB 제약/트리거), 이상 패턴 모니터링 |
| **허위 리뷰·피드백** | 피드백은 **비공개**이며 공개 평점/리뷰 없음 → 허위 후기의 공개적 영향은 제한적. 신고 기능, 안내 문구 | 기업의 자사 서비스 자기 피드백 방지(기업 계정은 customer 전용 정책으로 이미 차단), 신고 처리 SLA, 위반 계정 정지 정책 |
| **쿠폰 악용** | 사용자당 1회(부분 유니크 인덱스), 수량 초과 방지(행 잠금+CHECK), 1회 사용 처리, 코드 8자 난수 | 코드 사용 시도 횟수 제한(추측 방지), 취소/환불 정책, 다중 계정 방지와 연동한 혜택 어뷰징 탐지 |
| **보상과 평가 분리** | 감사 혜택(`thanks`)은 env + DB 설정 모두 false 가 기본. 혜택 발급은 감정/평점을 읽지 않음. **신규:** 혜택 문구에 평점·리뷰·긍정 평가·앱스토어 등이 있으면 서버에서 거절 | 키워드 필터는 우회 가능 → 관리자 승인 체크리스트(이미 표시)와 위반 제재 절차 유지. `thanks` 활성화는 법률 검토 후 별도 결정 |
| **개인정보** | 기업에는 이름·이메일 없이 익명 식별자(UI). 단, DB 응답에는 `author_id`(무작위 UUID)가 포함되어 같은 기업 내에서 동일인 추적 가능 | 기업용 뷰/RPC 로 `author_id` 대신 서비스별 해시 식별자 제공. 삭제·익명화 절차 구현(2번) |
| **광고 표시** | `sponsored` 는 관리자만 설정(RLS), 탐색 화면에서 "광고" 라벨 + 일반 결과와 분리 | 광고 대가 수취 시 표시 문구·위치의 법률 검토, 추천 영역에는 광고가 섞이지 않음을 테스트로 고정 |
| 혜택 수량 | 기업이 승인 후 수량을 **늘리는 것은 재승인 없이 가능**(앱·DB 모두 허용) | 정책상 문제가 되면 수량 증가도 재승인 대상으로 변경 |
| 기타 | `X-Forwarded-For` 를 그대로 신뢰(스푸핑 가능), 혜택 사용 시각 판정은 앱/DB 시계 혼용 | 신뢰 프록시 설정, 시계는 DB 기준으로 통일 |

## 5. 실제 Supabase 로 검증할 항목 (미실시)
- [ ] 사용자 간 피드백 격리 (고객 A ↔ B), 기업 간 격리 (기업 A ↔ B)
- [ ] 권한 상승: `profiles.role` 수정, 메타데이터로 `admin` 가입 시도
- [ ] 기업의 혜택 자가 승인/수량·발급 수 조작 차단
- [ ] 쿠폰 동시 발급·중복 수령·타 기업 코드 사용 처리 차단
- [ ] 이메일 확인 ON/OFF 상태별 가입·로그인 흐름, JWT 만료/갱신
- [ ] anon 키로 접근 가능한 테이블/함수 목록 전수 점검 (Supabase Security Advisor)
